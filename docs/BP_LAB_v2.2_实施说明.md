# BP LAB v2.2 实施说明

> 对应文档：《BP LAB v2.2：以 OP.GG 官方 MCP 为核心的轻量 BP 分析方案》（2026-11-11）
> 实施日期：2026-11-11　｜　版本口径：Data Dragon `16.22.1` / 官方补丁 `26.22`（两者版本号不同，页面分开标注）

## 0. 一句话结论

v2.2 的核心不是"再算一遍 OP.GG 已经算好的东西"，而是**把官方统计原样接入、把 BP LAB 的增值放在结构解释、缺口发现和候选建议上，并且不编造胜率**。

为此这次改造**删掉**了上一轮的两个数字出口：

| 删掉的 | 原因（v2.2 条款） |
|---|---|
| 「阵容强度 ±N pp」（五人胜率差的均值） | §2.1 不可把英雄胜率减 50% 当团队增益；§2.4 不再把五人均值当真实战力 |
| 「综合 0–100」启发式指数 | §6 禁止输出"无依据的统一体系强度指数" |
| 网页协同快照作为回退（`synergies.json`） | §2.2 位置不匹配的组合必须是 `UNKNOWN`，不能回退 |
| 时长桶 `±5pp` 截断 | §1.2/§8 改为**标记**异常桶（`LOW_SAMPLE_SUSPECT`）并从结论中排除，而不是把数据剪掉装正常 |
| `champions.json` 的"韩服大师+"标签套用到 MCP 数据 | §5.1/§8 MCP 响应没有返回地区/段位，就不能标"韩服大师+" |

## 1. 交付物

```text

bp.html                       BP 工作台（英雄池 / 双方阵容 / 结构与证据分析）
app.js                        仅负责 DOM 渲染与交互，不再做统计聚合
engine.js                     纯函数分析引擎（浏览器 + Node 共用，可测试）
styles.css                    v2.2 卡片样式
data/bp_rules.json/.js        维度定义、缺口规则、体系相克规则、候选分层、免责文案
data/champion_traits_v2.json  人工审核的战术标签（59 个热门英雄 × 10 维）
data/bp_contract.json/.js     合并后的前端合约（来源 / 口径 / 统计 / 时长桶 / 标签）
data/bp_lab_v22.sqlite        最小数据合同：source_snapshot / champion_traits / bp_analysis_cache
```

旧的 `data/champions.json`、`data/opgg_mcp.json`、`data/synergies.json` 作为**原始快照**保留，但前端不再直接加载；所有展示数据都经过 `bp_contract.json` 中转，以便统一挂上来源与口径字段。

## 2. 架构落地（对应 §1）

```text
OP.GG MCP 快照 (opgg_mcp.json)  ─┐
OP.GG 网页快照 (champions.json) ─┼→ scripts/build_v22_contract.py → bp_contract.json + bp_lab_v22.sqlite
人工审核标签 (champion_traits_v2)─┘                                        │
                                                                          ▼
                                                            engine.js（组合分析引擎）
                                                                          │
                                                          app.js（只负责渲染与交互）
```

- 构建器是**唯一**写合约的入口，手改 `bp_contract.js` 会在下次构建被覆盖。
- 引擎不读取原始网页快照，也不需要网络；所有来源信息随合约下发。
- 双击 `index.html` 打开首页，进入工作台；也支持 `python3 -m http.server 8080`。

## 3. 数据合同（对应 §4）

### 3.1 `source_snapshot`（一次官方响应 = 一行）

| 字段 | 本次取值 | 说明 |
|---|---|---|
| `provider` | `OPGG_MCP` / `OPGG_WEB_LEGACY` | 两类来源分开登记 |
| `tool_name` | `lol_get_champion_analysis` 等 | 便于追溯是哪次工具调用 |
| `requested_cohort` | `{tier: master_plus, region: 未指定}` | 只记录**请求**时给的条件 |
| `confirmed_cohort` | `null`（MCP） | 响应没有确认地区/段位，就不填 |
| `payload_hash` | sha256 | 只存哈希，原始 payload 留在文件里，避免 DB 重复膨胀 |
| `field_semantics_status` | `UNVERIFIED` / `LEGACY_AGGREGATE` | 字段含义是否被核对过 |
| `sample_n` | `null` | 源端没有桶级样本量，不从胜率反推 |
| `usage_review_status` | `PENDING` | OP.GG 条款尚未完成最终核对 |

### 3.2 `champion_traits`（人工审核标签）

- 主键：`(champion_key, role, patch, dimension)`；`role='*'` 表示"默认值"，角色行只覆盖有差异的维度。
- `level ∈ {WEAK, MEDIUM, STRONG, UNREVIEWED}`；`review_status ∈ {REVIEWED, PROVISIONAL, REVIEW_REQUIRED}`。
- 覆盖：59 个当前 BP 高热度英雄、10 个维度，共 570 条已审核 + 其余 1,160 条明确标为未审核（全 173 英雄）。
- 未审核**不会**被当成中性值：`UNREVIEWED` 直接让该维度的缺口规则不触发（见测试 R1）。

### 3.3 `bp_analysis_cache`

表已建好，本版尚未写入缓存行——当前每次渲染是纯前端计算（毫秒级），没有需要跨会话复用的昂贵调用的组合。等接入按需 MCP 查询时，用 `(draft_state_hash, rule_version)` 作为键写入。

**没有创建** `matches` / `participants` / `rank_snapshots` 等逐局大表（§4.3 明确不建）。

## 4. 分析能力（对应 §2）

| 能力 | 实现 | 关键约束 |
|---|---|---|
| 单英雄与版本（§2.1） | 英雄浮层显示胜率/选取/禁用/梯队/排名/场次 + 抓取时间 | 全部标注「口径未确认」，不写"韩服大师+" |
| Combo（§2.2） | 「协同分析」弹窗，按 `(英雄, 位置)` 精确匹配 | 缺失→`未提供`；只有其他位置记录→`POSITION_MISMATCH`；组合胜率**不**汇入任何队伍总分 |
| 对位（§2.3） | 「对位分析」弹窗，只比同路 | 默认以蓝方视角；只能拿到对手记录时反向换算并标 `反向` |
| 前中后期（§2.4） | ~~图表改为每个英雄一条线~~ → **2026-11-12 已整块下线**（校验未通过，见 §13） | 不再展示任何时间强度曲线 |
| 阵容体系（§2.5） | 10 维 × {弱/中/强/未审核}，双方并排 | 不合成"体系总分"；附加伤害类型与操作难度两项结构检查（不纳入总分） |
| 体系相克（§2.6） | 规则带 `trigger / reason / counterexample / reviewedPatch` | 只有机制解释，没有"Poke 对 Engage 胜率 61%" |

时长桶的可信度处理：

```text
rate <= 0 或 rate >= 100        → LOW_SAMPLE_SUSPECT
|rate - 该英雄自身均值| > 5pp   → LOW_SAMPLE_SUSPECT
```

被标记的桶在图表上打虚线/不画线，在「成员趋势」里计入 `⚑N` 并从阶段数值中排除，同时保留原因文案；`sampleN` 恒为 `null`，因此界面**不显示任何置信区间**。

## 5. 候选推荐（对应 §3）

「选人建议」弹窗按四层排序，**不计算综合分**：

1. **LEGAL**：可用英雄、位置合法、未被 Ban/已被选；
2. **GAP**：补上当前 HIGH/MEDIUM 结构缺口的具体维度（附缺口标题）；
3. **META**：同口径下的 OP.GG 分路表现（梯队、排名、胜率、场次）；
4. **RISK / UNKNOWN**：同路对位劣势、标签未审核、该分路无统计、敌方位置未锁定。

每张候选卡固定展示：补位理由、官方统计、已知协同（含场次）、对位状态、风险、未知项、四层标签。页面底部固定 `not calibrated` 文案。

## 5.5 下一手预测（适配度拆解）

v2.2 禁止的是"伪装成胜率的预测"，不是"按规则给出建议"。因此预测做成**可拆解的适配度**：

```text
适配度 = 20 × 阵容缺口补位
       + 10 × 与已选队友的官方协同
       +  5 × 同路对位（敌方该位置已锁定）
       + 15 × 同口径官方分路表现
       + 10 × 伤害类型平衡
       + 40 × 分路热门度（选取率）
       −  5 × 非首选分路校正（显式扣除，不藏）
```

> 这组权重不是拍脑袋定的，是用 508 局真实排位数据做 70/30 时间切分、144 组网格搜索得到的（见 §11）。
> 改动前是 `gap 35 / combo 20 / counter 15 / meta 20 / damage 10 / popularity 0`，命中率 18.3%；
> 当前配置 25.3%（验证集 25.8%）。

关键实现细节：

| 规则 | 做法 |
|---|---|
| 缺失项 | 退出分母后按覆盖权重算，`points = null`，绝不当 0 分（测试 R6） |
| 覆盖率 | `已覆盖权重 / 100`，同时决定置信度：≥85% 高、≥60% 中、否则低 |
| 缺口补位 | 3 人以上用正式缺口规则（HIGH=3 / MEDIUM=2 加权）；不足 3 人用"各维度最强值"的结构短板（1 人起可用） |
| 协同 | 只认官方返回的组合；没有记录就标记"未提供"，不加分也不减分 |
| 对位 | 仅在敌方该位置已锁定时参与；反向记录会标注 |
| 版本表现 | 同分路内排名百分位 60% + 胜率极差百分位 40% |
| 伤害结构 | 已选 2 人起判断，队伍单一 AP/AD 时才作为区分项，已平衡视为中性 |
| 未审核标签 | 候选该维度未审核 → 该项不加不减，同时降低覆盖率 |
| 热门度 | 分路选取率 / 该分路最高选取率；调参后发现它是单排命中的主导项（见 §11） |

界面两处：

1. **英雄池上方的预测条**：实时显示当前这一手 Top 5（适配度 + 置信度 + 覆盖率），点一下直接选人。
2. **「预测」按钮**：打开完整拆解，每个候选列出 5 项的 `得分 / 权重`、证据、风险与未知项。

置信度会随数据缺失下调，而不是用中性值补齐；模型版本 `fit-v2.2.1` 与权重写在 `data/bp_rules.json` 的 `fit` 字段里，改权重不用改代码。

## 8. 数据覆盖与限制

1. **口径未确认**：MCP 响应没有 `region` 参数，`meta.region` 自述为 "not specified by MCP (likely global/default aggregate)"。因为不能确认，所以页面显示「口径未确认」，而不是沿用旧快照的"韩服大师+"。
2. **时长曲线仍是旧快照**：253 条英雄-分路曲线来自 OP.GG 网页快照（`LEGACY_AGGREGATE`，自述韩服大师+、16.22），与 MCP 的统计**不是同一口径**，两者在界面上分开标注、不相加。
3. **没有桶级样本量**：无法给出 Wilson 区间，也不做跨英雄曲线排名；只能作为单英雄趋势并列参考。
4. **标签覆盖 59 / 173**：热门池已审；未覆盖英雄的 10 维一律 `UNREVIEWED`，结构分析会显示"标签未审核"而不是"没有缺口"。
5. **新英雄未核对**：`yunara`（芸阿娜）、`locke`（洛克）机制未确认，10 维全部 `UNREVIEWED`。
6. **`tahmkench` 上单无时长曲线**：旧快照抓取时就缺失（`meta.failures`），界面显示"无时长统计"。
7. **候选排序未做人工反馈校准**：目前是规则排序，不是学习排序器（§3.2 的可选后续）。
8. **旧启发式标签已降级**：`data/champion_traits.json`（关键词/属性派生）不再进入任何评分，只作为参考材料；产品只用 `champion_traits_v2.json`。
9. **条款状态 `PENDING`**：OP.GG ToU 对数据存储/展示/再分发的要求尚未最终核对，正式对外部署前需要复核；本版只做本地低并发读取，没有爬虫行为。

## 17. 实时比赛条（2026-11-12）

### 17.1 数据链路

- **轮询器**：`scripts/live_poller.mjs`，无头 Chrome 打开 lolesports.com，借页面同源的
  `lolesports.com/api/gql`（持久化查询 `homeEvents`）取比赛，**每 20s** 写
  `data/live_matches.json` / `.js`。
- 为什么不直接 curl：`esports-api.lolesports.com` 在本机返回 **403**；同源 GQL 稳定 200。
- **第二数据源**：`scripts/fetch_esports_results.py` 用 OP.GG MCP 拉
  `lol_esports_list_schedules`（mode=result / schedule），补上 lolesports 不返回的**队名与比分**，
  写 `data/esports_results.json`；由轮询器每 30 分钟自动刷新一次。
- 容错：浏览器崩溃自动重启；10 分钟强制重建页面；单条查询失败不影响其他查询。

### 17.2 首页（index.html）

新的默认入口是 `index.html` 仪表盘：

- 顶部：版本、口径、标签覆盖 + 「进入 BP 工作台」
- 「实时比赛」：lolesports 的进行中比赛（LIVE）+ OP.GG 的未开始赛程（带队名，如 BLG vs GEN）
- 「最近比赛」：OP.GG 结果（队名 + 比分 + 日期），如 BLG 3:1 T1
- BP 可用时显示 10 个英雄头像
- 「版本胜率」：按分路切换，列出胜率与选取率（OP.GG 16.22，口径未确认）
- 「开始分析」：自由 BP / 标准 BP / 验证报告入口

`bp.html` 是原来的 BP 工作台，顶部保留 34px「实时比赛」条（紧凑版）。

- 进行中（LIVE）/ 未开始（时间）/ 最近结束 的比赛 chip：联赛 + 时间 + 轮次/对阵
- 右侧「版本胜率 TOP」：OP.GG 16.22 英雄-分路胜率前 6（口径未确认）
- 前端每 20s 重载 `data/live_matches.js` 刷新，无需整页刷新

4. BP 仍可在主界面手动录入，结构/对线/阶段分析照常实时计算。

## 16. 胜率与强度分开：对线强度模块（2026-11-12）

用户反馈：**胜率和强度要分开，强度是一眼能看出来的（如 EZ+卡尔玛前期比霞洛强）**。

### 16.1 定位

| 概念 | 数据 | 用途 |
|---|---|---|
| 胜率 | OP.GG 历史胜率 | 弱先验（职业 8,800 局 AUC 0.515），不做预测 |
| **对线强度** | 职业赛 15 分钟经济差（ChainCC） | 描述对线期作战能力，带 n 与 CI |

### 16.2 实现

- 单人：`data/lane_stats.json`（142 英雄 / 202 分路，n≥20）
- 下路双人：`data/lane_duos.json`（239 组合，n≥10，ADC+辅助合计）

### 16.4 规则型阶段曲线（已上线，标注为“规则推断”）

用户确认「有大致曲线就够了」，因此上线一条**规则推断型**阶段曲线：

- 权重（写死在 `engine.js`，可审）：

## 15. 胜率的比赛级校验（2026-11-12）

按 GPT 建议，把胜率校验从"英雄分档 + 相关"改成**比赛级差分回归**：

```text
X_g = 蓝方五人报告胜率均值 − 红方五人均值（pp）
logit P(蓝方胜) = α + β·X_g     （职业按补丁去均值）
```

| 数据集 | 对局 | β/pp | OR/pp | AUC | CV log-loss 改善 | Q4−Q1 |
|---|---|---|---|---|---|---|
| 排位 16.20–22 | 996 | 0.218 | 1.243 | 0.552 | +0.00449 | +14.1pp（CI 5.6~22.9） |
| 职业 2026 | 8,800 | 0.059 | 1.061 | **0.515** | +0.00033 | **+1.9pp（CI −0.8~5.1）** |
| 职业 26.20–22 | 241 | 0.205 | 1.227 | 0.547 | −0.00747 | +7.3pp（CI −10~23） |

**结论**：职业侧的干净估计显示胜率只带来约 +1.9pp 的四分位差、AUC 0.515；排位的 +14pp 由极值英雄（悠米等）与玩家水平混杂驱动，不能采信。胜率定位为**弱先验**，不进入任何"预测胜率"输出。

## 12. 曲线与胜率的校验（16.20–16.22 窗口）

### 12.1 口径

按“16.20 → 16.22 变化不大”的假设，把 **2026-10-08 起**（16.20 首场）作为同一窗口；同时给出严格 16.22（2026-11-05 起）子集做稳定性对照。

| 数据 | 样本 | 说明 |
|---|---|---|

### 12.2 结果

| 检验 | 排位 16.20–22 | 排位 严格 16.22 | 职业 26.20–22 |
|---|---|---|---|
| A 胜率相关 / 四分位差 | 0.228 / **+4.6pp**（48.3→52.9） | 0.305 / **+5.0pp** | 0.248 / +1.9pp |
| B 曲线“偏后期”相关 | **−0.012**（加权 0.063） | 0.079（加权 0.122） | 0.166（加权 0.143） |

| D 分桶相关 / 正偏差侧实际值 | 0.127 / **+3.27pp**（CI 1.08–5.44） | 0.151 / **+3.71pp**（CI 1.26–6.14） | 0.033 / 样本不足 |

### 12.3 结论

1. **胜率是弱但稳定的先验**：两个排位子集分别 +4.6pp / +5.0pp（最高档 − 最低档），相关 0.23 / 0.31。可以保留在界面上，但不能当“预测胜率”。
2. **时长曲线不可用**：排位窗口内相关 −0.01（严格 16.22 为 0.08），三档长短局差没有单调性；队伍级合成 52–55%，置信区间全部包含 50%。之前 981 局时看到的 0.20 是样本波动。
3. **分桶正偏差侧有弱一致性**：曲线说“+2pp 以上强”的桶，实际 +3.3~3.7pp；但负偏差侧不成立，因此只能单向使用，且强度不足以支撑推荐。

### 11.3 调参与结论

- 144 组权重、70/30 时间切分网格搜索，训练集最优 = `gap20 / combo10 / counter5 / meta15 / damage10 / popularity40`，验证集 Top5 **25.8%**、MRR 0.175。
- **纯热门度**（popularity=100）单独跑：Top5 25.0%、MRR 0.169。
- 也就是说，单排"下一手"主要由**热门度**解释；适配项（缺口/协同/对位/伤害）合计只贡献约 **+0.3~0.5pp**，落在抽样噪声（Top5 标准误约 ±0.6pp）内。
- 已把该配置写入 `data/bp_rules.json`，并把 `popularity` 暴露为可见的评分项（弹窗里能看到每一项得分）。

### 11.4 怎么理解这些数字

1. **Top1 只有 5.9% 不代表系统坏了**：每个位置有 30–40 个合法候选，随机 Top1 约 2.5%、Top5 约 10.3%；系统 Top5 是随机的 2.5 倍。
2. **它预测的是"玩家实际会选什么"，不是"选什么能赢"**。单排玩家大量重复自己的主玩英雄，热门度天然占优；这不构成"适配度越高胜率越高"的证据。
3. **前两轮几乎无信息**（0 人时只有热门度/版本），第 4 手（已选 3 人）时适配信息最充分，Top5 冲到 39.4%。
4. 样本是韩服单排，与职业 BP 的选人分布差异很大；职业场景需要另行采集。
