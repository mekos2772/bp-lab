# BP LAB 审计采纳清单（Reference）

> 用途：作为 BP LAB 下一轮迭代的“参考基线”，用于判断哪些审计意见立即采纳、哪些需要修正、哪些暂缓。
>
> 对应文档：`docs/BP_analysis_review.md`（原评估报告）与 `deep-research-report.md`（外部审计报告）

---

## 1. 总体决策

**采纳核心结论：**
> 当前 BP LAB 是“描述性阵容分析原型”，不是经过校准的胜率预测器；应保留现有解释型 UI，同时新建比赛级、可回测、可校准的预测层。

**不采纳的做法：**
- 不继续在 `TeamCurve + pairDelta` 上叠加更多手工启发式分数，然后称为“预测”。
- 不把 Data Dragon 技能关键词自动生成的标签直接当成战术体系标签。
- 不先上 GNN / 复杂深度模型。
- 不把 OP.GG 抓取当作长期商业数据基础。

---

## 2. 立即采纳（P0）

| 事项 | 具体动作 | 验收标准 |
|---|---|---|
| 指标改名 | “阵容强度” → “阵容方向性指数”；“胜率曲线” → “历史条件胜率趋势”；“协同指数” → “双英雄历史组合表现” | UI 不再出现“预测胜率”字样 |
| 数据合同 | 每条 rate 保存 `source_url / source_version / fetched_at / role / sample_n / field_semantics_verified` | 可追溯到具体页面与抓取时间 |
| 不确定性 | 用 Wilson / Jeffreys / Beta-Binomial 收缩替代硬阈值与 clamp | 低样本组合自动向均值收缩，并显示区间 |
| 目标定义 | 明确区分：BP 前预测、BP 完成后评估、进行中下一手推荐、时长条件胜率 | 文档/ API 中各目标有独立字段与命名 |
| 回测 | 用 forward-only split，按 patch、series、player 分组 | 报告 log loss / Brier / AUC / ECE / 校准曲线 |
| 基线 | 至少跑：50% baseline、side-only、hero-role main effects、当前 heuristic、logistic full | 复杂模型没有超越基线就不上线 |
| 合规 | OP.GG ToU 审查；优先迁移 Riot Match-V5 / 授权数据 | 数据来源有授权记录或明确许可 |

## 3. 采纳但需要修正的审计表述

| 审计报告的说法 | 修正说明 |
|---|---|
| “原报告认为 50 场过滤基本解决小样本问题” | 原报告已明确：50 场只是工程过滤，±5/±8 是 display clamp，不是统计解决方案。审计此处略有稻草人。 |
| “原报告认为所有时长桶因为生存者偏差不能用于预测” | 原报告写的是“适合趋势参考，不能直接解释为实时战斗力”，并未说完全不能用于任何预测。 |
| “审计已独立验证 173/253/10,160 等数据” | 审计自己承认这些是报告自述数据，未重新抓取；因此它是方法审计，不是数据复核。 |
| “10 万场足以稳定估计所有英雄×分路×组合×对位” | 这句话来自原报告的过度概括，审计纠正正确；10 万场只够训练正则化 baseline，不足以独立估计所有交互。 |
| “Patch 16.22” | 应写成“游戏公开补丁 26.22 / Data Dragon 资源版本 16.22.1”。 |

## 4. 暂缓或后置

| 事项 | 原因 | 建议时机 |
|---|---|---|
| 层次贝叶斯全量模型 | 需要稳定的比赛级数据与先验结构 | 在 logistic baseline 通过后 |
| GBDT / CatBoost / LightGBM | 作为 challenger 有价值，但不是第一版必需 | baseline 完成后再比较 |
| GNN / 图神经网络 | bottle neck 是标签与数据质量，不是模型容量 | 暂不作为路线 |
| 完整 90 天数据仓库 | 对原型过重；先做最小数据合同与回测 | 用户确认要 production 后 |
| Fearless / BO5 系列赛模型 | 需要赛事规则与系列赛数据 | 有职业数据后 |

## 5. v2 最小可行架构

### 5.1 数据

- 来源：Riot Match-V5（韩服 Master+，按版本切片）或授权赛事数据
- 每局字段：
  `game_id, patch_public, ddragon_version, region, queue_id, start_ts, duration_s, blue_win, data_source`
- 每名参与者：
  `game_id, puuid_hash, side, role, champion_id, pregame_rank`
- 选人/禁用：
  `draft_picks(game_id, pick_order, side, champion_id, inferred_role, role_probability)`
  `draft_bans(game_id, ban_order, side, champion_id)`
- 特征：
  `hero_role_effect, pair_residual, lane_matchup, comp_archetype, structure, player_champion_proficiency`

### 5.2 模型

```text
logit(P(Blue win)) = β0 + β_side
  + Σ α(hero, role)        # 主效应，强正则
  + Σ γ(pair, residual)    # 双人协同残差
  + Σ δ(lane matchup)      # 对位
  + Σ θ(comp archetype)    # 体系/结构
  + Σ μ(player, champion)  # 选手熟练度（仅历史信息）
  + ε
```

### 5.3 评估

- 时间切分：`train p1..pk / valid pk+1 / test pk+2`，滚动前进
- 指标：Log Loss、Brier、AUC、ECE、reliability diagram
- 分组：patch、rank、side、role、duration、confidence
- Bootstrap：按 game / series / player cluster，不按 pair row

## 6. 指标与产品文案对照

| 现在 | 建议 |
|---|---|
| 阵容强度 | 阵容方向性指数 |
| 胜率曲线 | 历史条件胜率趋势 |
| 后期强度 | 长局条件表现 |
| 协同指数 | 双英雄历史组合表现 |
| AI 推荐 | 候选建议（top-k + 理由 + 不确定性） |
| 预测胜率 | 校准完成前禁止出现 |

## 7. 体系标签的约束

- Data Dragon `tags`、`info`、技能文本只能作为 **弱监督种子**，不能直接当真实战术标签。
- 当前 `champion_traits.json` 已出现误判示例：
  - Jayce 的 Poke 标签被漏掉（远程/近战形态差异）
  - Fiora 的 self-heal 被误算成 team peel
  - 大量“护盾/治疗”关键词会把自我续航算成团队保护
- 体系标签必须是 **0-1 连续强度 + 人工校准 + 版本化**，不能只存 Boolean。
- 体系评分建议用 geometric mean 起步（缺一项就明显降分），例如：

```text
Score_poke = (poke^1.5 * waveclear * disengage * siege)^(1/4.5)
```

## 8. 开放问题

1. OP.GG `rate` / `average` 字段的真实语义与样本量口径。
2. Data Dragon `16.22.1` 与官方 `Patch 26.22` 的双版本映射规则。
3. OP.GG ToU 与帮助中心说明存在冲突，商业使用需书面许可。
4. 当前 50 场过滤后的组合样本中，有多少能进入模型训练/验证。
5. 职业赛与韩服大师+ 是否应完全分开建模（当前判断：应分开）。
