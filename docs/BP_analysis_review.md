# BP LAB 分析方法评估报告

> **用途**：把当前 BP LAB 的数据、算法、结论和缺口整理成一份自包含文档，方便交给 GPT / 其他分析模型做审查。
>
> **版本**：2026-11-11 · Patch 16.22 · 韩服大师+ 数据快照
>
> **对象**：`BP LAB` 当前版本的“英雄强度曲线 + 阵容协同 + 阵容诊断”分析。

---

## 0. 给审查者的摘要

**当前系统是什么：**
一个 LoL BP 模拟器 + 阵容强度分析工具。选人时实时读取 OP.GG 的英雄分路胜率与游戏时长曲线，叠加双人协同胜率，绘制双方前中后期曲线，并给出“后期核心 / 前期节奏 / 均衡阵容”等标签。

**一句话评价：**
> 作为**数据可视化 / 方向性分析原型**，工程完成度较高、数据量可观；作为**可验证的 BP 预测模型**，目前数据与方法都不够，结论只能算“启发式估计”，不能称为可信预测。

**最关键的 5 个问题：**
1. **加性假设**：队伍强度 = 5 个英雄胜率的平均，忽略英雄之间的交互、对位和阵容体系。
2. **时长曲线存在生存者偏差**：前期阵容会把对局提前结束，因此“40+ 分钟胜率”并不等于“后期强度”。
3. **小样本极值严重**：40+ 分钟桶的胜率差最小值 -50pp、最大值 +50pp，253 条曲线中有 172 条绝对值 >5pp；低样本噪声主导曲线。
4. **缺少对位与体系层**：没有 lane counter / 2v2 / 分带 / Poke / 强开等结构指标，无法解释“为什么这手 pick 好”。
5. **没有回测**：没有用真实比赛结果检验预测，无法给出准确率 / 校准度 / 置信区间。

## 1. 当前分析到底做了什么

### 1.1 数据来源与规模

| 数据 | 来源 | 规模 | 抓取时间 |
|---|---|---|---|
| 英雄分路时长曲线 | OP.GG 英雄趋势页（韩服 KR / 大师+ / Patch 16.22） | 173 英雄、253 条分路曲线、每条 5 个时长桶 | 2026-11-11 19:02 |
| 双人协同胜率 | OP.GG 英雄协同页（同一口径） | 254 个页面、10,160 条组合记录、24,698 个索引 | 2026-11-11 19:27 |
| 英雄标签/属性/技能关键词 | Riot Data Dragon 16.22.1 `championFull.json` | 173 英雄 × 9 类启发式标签 | 2026-11-11 19:36 |

**时长桶**：
`<25 分钟 / 25-30 / 30-35 / 35-40 / 40+ 分钟`

### 1.2 核心公式（当前代码实际实现）

**单英雄强度差：**

```text
delta(champion, role, bucket) = clamp(rate - 50, -5, +5)
```

- `rate`：OP.GG 页面「胜率随时间」曲线中的胜率值（按页面展示理解）
- `average`：页面给出的英雄平均基准，实际数据中恒为 50.0
- `clamp ±5pp`：工程上为抑制低样本极端值

**队伍强度曲线：**

```text
TeamCurve(bucket) = mean(delta of all picked champions in team)
```

**前中后期：**

```text
Early = TeamCurve(<25)
Mid   = (TeamCurve(25-30) + TeamCurve(30-35)) / 2
Late  = (TeamCurve(35-40) + TeamCurve(40+)) / 2
```

**队伍总强度（仅用于显示）：**

```text
TeamScore = mean(TeamCurve over 5 buckets)
```

**双人协同指数：**

```text
pairDelta = clamp(pairWinRate - 50, -8, +8)
Weight    = sqrt(pairGames)
TeamSynergy = sum(pairDelta * Weight) / sum(Weight)
```

- 只统计 `pairGames >= 50` 的组合
- 组合数据从 OP.GG 协同页按「本英雄位置 × 搭档位置」匹配
- 精确位置对不上时回退到 `ANY` 组合（忽略位置）

**阵容风格标签：**

- `Early - Late > 0.7` → 前期节奏 / 前中期节奏
- `Late - Early > 0.7` → 后期核心 / 中后期核心
- 峰值在中期 → 中期节奏
- 否则 → 均衡阵容
- 同时输出团队峰值阶段和“核心英雄”

### 1.3 当前产品输出

- 双方 5 个位置 + 5 个 Ban
- 实时强度曲线（蓝/红）
- 前中后期三张阶段卡
- 英雄“前期/中期/后期”标签
- 双人协同弹窗（协同指数 + 最佳/最差组合 + 样本场次）
- 20 手 BP 进度条

## 2. 正确性审查

### 2.1 逻辑上成立的部分

1. **同口径比较**：蓝红双方都使用同一版本、同一地区、同一段位的数据，横向比较有基本公平性。
2. **分路拆分**：同一个英雄不同位置使用不同曲线，避免了“中单阿狸”和“辅助阿狸”混用。
3. **双人协同是真实数据**：不是手工编的 synergy 分，而是 OP.GG 的实际双人组合胜率。
4. **低样本过滤**：协同数据过滤 <50 场，避免明显的 1-2 场组合。
5. **产品可解释**：每个数字都能回溯到英雄/分路/时长桶，用户能理解来源。

### 2.2 不成立或未经证实的强假设

#### 假设 1：队伍强度 = 5 个英雄强度的平均

这是当前模型最大的问题。英雄之间存在明显交互：

- 石头人 + 亚索 / 发条：单看胜率不是简单相加
- 卡莎 + 洛、卢锡安 + 娜美：双人组合有配合价值
- Poke 阵容需要反手/清线，单看每个英雄胜率会把“体系不全”的阵容算高
- 全 AD 阵容遇到坦克会明显贬值，但单英雄胜率不会反映这一点

**结论**：加性模型只能作为 baseline，不能作为最终 BP 预测。

#### 假设 2：英雄胜率 = 英雄强度

胜率受很多因素影响：

- 玩家熟练度（尤其高分段）
- Pick 率 / Ban 率导致的选择偏差
- 队伍阵容与对局时长
- 版本红利 / 新英雄保护
- 对手水平

**结论**：胜率是“结果指标”，不是“因果强度”。如果只拿胜率做预测，会把“热门英雄”误当成“强英雄”。

#### 假设 3：时长桶胜率 = 该时间点的强度

- 前期阵容会更快结束比赛，因此他们的“40+ 分钟局”往往是少数被拖到后期的局，样本存在生存者偏差。
- 后期阵容的“<25 分钟局”也往往是崩盘局，不是正常强度。
- 35-40 / 40+ 桶的样本量通常远小于 25-30 / 30-35 桶。

**结论**：曲线适合做“趋势参考”，不能直接解释为“英雄在第 N 分钟的实时战斗力”。

#### 假设 4：双人协同胜率 - 50 = 协同价值

- OP.GG 的 `win_rate` 是双人组合的原始胜率，仍包含两个英雄各自的强度、玩家熟练度、对局环境。
- 没有做“相对于两个英雄各自基准胜率”的差值，因此不能完全归因于“协同”。
- 只覆盖双人组合，不覆盖三人/四人/五人体系。
- 许多组合样本量在 50-100 场之间，置信区间很宽。

**结论**：协同指数有参考价值，但不能当作严格的“1+1>2”度量。

#### 假设 5：BP 可以脱离对手单独评分

当前 `TeamCurve` 只计算己方 5 个英雄，不考虑敌方 5 个英雄。真实 BP 是零和的、对位驱动的：

- 先选亚索，对方后手选石头人/布隆，价值完全不同
- 先选 Poke 阵容，对方强开/突进，价值完全不同
- 先选分带英雄，对方有全球流/强开，价值完全不同

**结论**：当前模型没有“matchup”和“counter”维度，不能做真正的 BP 价值判断。

#### 假设 6：`average = 50` 和 `rate` 字段语义已经确认

当前代码把 OP.GG 页面里的 `rate` 当作胜率、`average` 当作 50 基准。但：
- OP.GG 未提供公开字段说明
- 页面可能是“相对胜率”或经过归一化的值
- `rate` 实际出现 0% 和 100% 的极端值（低样本）
- 需要向 OP.GG 或通过独立样本验证字段定义

**结论**：这是一个未验证的数据假设，需要在报告中标注。

### 2.3 数据层面的硬伤（可直接复核）

| 检查项 | 结果 | 含义 |
|---|---|---|
| 40+ 分钟曲线极值 | 最小 -50.0pp，最大 +50.0pp | 极端值基本来自低样本 |
| 40+ 桶绝对值 >5pp 的曲线 | 253 条中 172 条（68%） | 大多数英雄 40+ 数据噪声很大 |
| 40+ 桶 p95 绝对值 | 约 40.0pp | 数据分布非常宽 |
| 0% 胜率桶 | 9 个（如墨菲特中单 40+、库奇中单 40+） | 样本极少 |
| 100% 胜率桶 | 3 个（如德莱厄斯打野 40+、茂凯打野 40+） | 样本极少 |
| 协同组合中位样本量 | 约 45 场 | 一半组合不到 50 场 |
| 协同组合 ≥50 场（去重后） | 约 4,144 条 | 可用数据量中等 |
| 协同组合 ≥500 场（去重后） | 仅 78 条 | 高置信组合很少 |

> 这些数字说明：**40+ 分钟段和大量协同组合的统计可靠性不足**，±5pp / ±8pp 截断是工程补丁，不是统计解决方案。

## 3. 数据支撑够不够

### 3.1 分用途判断

| 用途 | 是否足够 | 说明 |
|---|---|---|
| 查看英雄大致强势期 | **够**（方向性） | 253 条分路曲线，当前版本 |
| 比较两个英雄的时长趋势 | **中等** | 可看趋势，不能读绝对值 |
| 评估一套阵容的强度曲线 | **不够** | 加性平均 + 生存者偏差 |
| 双人协同分析 | **中等** | 真实数据，但样本量/基线问题 |
| 体系识别（Poke/边带/强开） | **未实现** | 只有启发式英雄标签，尚无体系评分 |
| 对位/克制分析 | **未实现** | 未接入 counter 数据 |
| BP 预测/推荐 | **不足** | 没有真实对局标签、没有回测 |
| 选手/战队适配 | **未实现** | 无英雄池、选手熟练度、对手习惯 |

### 3.2 当前数据能回答/不能回答的问题

**能回答：**
- 这个英雄在韩服大师+、当前版本、各时长段的胜率大概是什么样？
- 这两个英雄一起出场时，历史双人组合胜率如何？
- 这套阵容的“平均英雄胜率曲线”长什么样？

**不能回答：**
- 这套阵容遇到对面这套阵容，谁优谁劣？
- 这套阵容是 Poke、边带、强开还是保护大核？体系完整吗？
- 这个选手/战队能不能把这套阵容打出来？
- 这手 Ban 的价值有多大？应该 Ban 版本 OP 还是 Ban 对手绝活？
- 这个预测的置信度是多少？准确率是多少？

## 4. 合理性判断

### 4.1 合理的地方

- 产品方向合理：BP 工具确实需要把“英雄强度、时长曲线、协同、体系、对位”分层展示。
- 数据工程合理：173 英雄、253 条分路曲线、1 万条协同记录，已经能支撑一个可用的原型。
- 可解释性合理：所有指标都能展开到具体英雄、分路、时长桶。
- 工程取舍合理：过滤低样本、截断极端值、展示样本量，说明作者知道数据有噪声。

### 4.2 不合理/过度宣称的地方

- 把“队伍平均胜率差”称为“阵容强度”，容易让用户误以为是真实胜率预测。
- 把“双人协同胜率 - 50”称为“协同指数”，没有做基线校正，可能把英雄本身强度误归因为协同。
- 目前没有体系识别，不能回答“这是 Poke 体系还是边带体系”。
- 没有对位数据，不能回答“这手 Pick 会不会被对面 Counter”。
- 没有回测，不能回答“这套模型预测准确率多少”。

### 4.3 总体评分（供参考）

| 维度 | 评分（10 分） | 说明 |
|---|---:|---|
| 数据覆盖 | 6.5 | 英雄曲线和协同数据不错，但缺对位/体系/选手 |
| 统计严谨性 | 3.0 | 无置信区间、无回测、加性假设 |
| 可解释性 | 8.0 | 每个指标可追溯 |
| 产品完成度 | 7.5 | UI 完整，能实时交互 |
| 预测可信度 | 2.5 | 只能做方向性参考 |
| **综合：作为原型** | **7.0** | 方向正确，适合迭代 |
| **综合：作为预测模型** | **3.0** | 需要重建数据与验证体系 |

## 5. 缺失因素与优先级

### P0（不做就无法称为预测）

1. **真实对局级数据**：Riot API / Oracle's Elixir 等，拿到每局双方 10 个英雄、位置、胜负、时长、段位、选手。
2. **回测体系**：按版本/时间切分训练集与测试集，报告 AUC、Log Loss、Brier、校准曲线。
3. **对位数据**：lane counter、2v2、打野路径、分路对位胜率/线杀率。
4. **体系标签**：强开团、Poke、分带、保护大核、抓单、突进、前期雪球、后期运营。
5. **样本量与置信区间**：每个时长桶/组合显示场次和置信区间，而不是只显示胜率。

### P1（显著提升解释力）

6. **BP 顺序价值**：蓝方首抢、红方末位、盲选、摇摆位、Counter 位。
7. **Ban 价值模型**：版本 OP、对手绝活、体系关键牌、Counter 位。
8. **选手英雄池 / 绝活 / 状态**。
9. **对手 BP 习惯**：常 Ban、常抢、常放、红蓝方偏好。
10. **版本趋势**：跨补丁的优先级变化，而不是单版本快照。

### P2（进阶）

11. 队伍风格（进攻/运营/团战/后期）。
12. 无畏征召 / BO3 / BO5 的英雄池消耗。
13. 训练赛/藏招/心理战。
14. 游戏内执行因素（线权、视野、资源交换）。

> 完整的 10 层 / 100+ 因素清单见附录 A。

## 6. 建议的 v2 模型架构

### 6.1 数据层

- 目标数据：韩服大师+、单排/职业赛、2026 赛季、按版本切片
- 每条样本：`patch, side, rank, player roles, 5 blue champions, 5 red champions, bans, winner, game_duration`
- 至少需要 **10 万+ 场** 对局，才能稳定估计英雄 × 分路 × 组合 × 对位效应；否则用层次贝叶斯收缩。

### 6.2 特征层

```text
champion_role_effect
+ pair_synergy
+ lane_matchup
+ comp_archetype_score
+ damage_balance
+ frontline/backline
+ cc/engage/peel/waveclear
+ power_spike_alignment
+ player_champion_proficiency
+ opponent_ban_priority
+ side / patch
```

### 6.3 模型层

推荐先用可解释模型：

```text
logit(P(win)) = β0
  + β_side * side
  + Σ α(champion, role)
  + Σ γ(pair)
  + Σ δ(matchup)
  + Σ λ(archetype)
  + Σ μ(player, champion)
  + ε
```

- 正则化：Elastic Net / 层次贝叶斯（把冷门英雄向全局均值收缩）
- 可选：梯度提升树（GBDT）做非线性交互，但必须做 SHAP 解释
- 评估：AUC、Log Loss、Brier Score、校准曲线、按版本/段位分组表现

### 6.4 产品层

- 将当前“启发式强度”标注为 **Heuristic / 方向性**
- 只有通过回测的模型才标注 **Calibrated / 预测**
- 每个数字显示样本量、置信区间、数据更新时间
- 推荐 pick 时显示“理由链”：版本强度 + 对位 + 体系 + 协同 + 选手熟练度

# 英雄联盟 BP 影响因素全清单

> 目的：给 BP LAB 的预测模型建立完整的输入维度，而不是只依赖“英雄胜率随时长曲线 + 双人协同”。

> 当前版本：Patch 16.22 · 数据参考 OP.GG 韩服大师+ · 文档更新时间 2026-11-11

---

## 0. 先给结论

一个完整的 BP 预测，至少要考虑 **10 个层面**：

1. **版本环境层**：补丁、装备/符文、地图资源、平均游戏时长、队列/段位/服务器
2. **英雄个体层**：胜率、Ban/Pick 率、分路胜率、时长曲线、难度、上限、摇摆位
3. **对位层**：线上克制、2v2/3v3、打野路径、团战克制、分带 vs 支援
4. **阵容体系层**：强开团、Poke、分带、保护大核、抓单、突进、团战 AOE、前期雪球、后期运营
5. **阵容结构层**：AD/AP、前排/后排、控制链、开团/反手、清线/推塔、机动性、视野、打坦、续航
6. **组合协同层**：中野、下路双人、上野、辅野、大招链、增益叠加、强势期同步、反协同
7. **BP 机制层**：蓝红方、Pick/Ban 顺序、盲选、摇摆、Counter 位、换位、无畏征召、BO 系列赛
8. **选手/战队层**：英雄池、绝活、状态、队伍风格、指挥、对手 BP 习惯、心理战
9. **数据质量层**：样本量、置信度、版本漂移、选择偏差、段位/地区差异
10. **执行层**：线权、打野路径、资源交换、视野、边线处理、团战站位（决定阵容能不能打出来）

> 当前 BP LAB 已有：英雄分路胜率、五档游戏时长曲线、双人协同胜率。
> **还没有**：体系识别、对位数据、阵容结构评分、选手/对手因素、BP 顺序价值模型。

## 4. 阵容体系层（核心）

这一层就是“边带体系、Poke 体系”应该被建模的地方。

| 体系 | 核心需求 | 强势期 | 主要克制 | 识别指标 |
|---|---|---|---|---|
| **强开团 / 团战 AOE** | 硬开团、前排、AOE 跟进 | 中期~后期 | Poke、分带 | 开团数、硬控、前排、AOE |
| **Poke / 消耗 / 攻塔** | 长手、清线、消耗、反开 | 中期 | 强开、突进 | 长手数、Poke 技能、清线、反手 |
| **分带（1-3-1 / 4-1）** | 1v1 强点、4 人守塔、传送/全球流 | 中后期 | 强开/抓单/传送支援 | 单带点、清线、1v1、TP |
| **保护大核（四保一）** | 大核、护盾/治疗/解控、前排 | 后期 | 突进/刺客/分带 | 大核、护盾、治疗、反手 |
| **抓单 / 视野压制** | 钩子/硬控、爆发、视野 | 中期 | 团战 AOE、反开 | 先手控制、爆发、扫描/视野 |
| **突进 / 冲阵 / 切后排** | 多突进、爆发、进场 | 中期 | 保护、反手、控制链 | 突进数、爆发、切后排能力 |
| **前期节奏 / 雪球** | 线权、打野节奏、越塔 | 前中期 | 后期阵容、防守反击 | 前期曲线、线权、越塔 |
| **后期运营 / 大后期** | 大核、清线、防守、龙魂 | 后期 | 前期雪球、快节奏 | 后期曲线、清线、防守 |
| **Wombo Combo** | 多个大招/控制链 | 中期 | 分散站位、水银/闪现 | 大招链、AOE 控制 |
| **拉扯 / 反打** | 反手、位移、控制 | 中期 | 强开、Poke | 反手控制、位移、续航 |

**体系识别不是看英雄名字，而是看功能标签**：
`开团 / 前排 / 后排输出 / 爆发 / 持续输出 / 控制 / 保护 / 清线 / 推塔 / 单带 / 机动 / 视野 / 续航 / 打坦`

> 目前已生成 `data/champion_traits.json`：从 Data Dragon 的英雄标签、基础属性和技能描述关键词，为 173 个英雄提取了 `frontline / backline / engage / peel / poke / splitpush / dive / sustain / waveclear` 等启发式标签。后续可继续人工校准。

## 5. 阵容结构层（Structure）

| 维度 | 目标 | 风险 |
|---|---|---|
| 伤害类型 | AD / AP / 真实 / 混合，避免单一 | 全 AD 被堆护甲；全 AP 被堆魔抗 |
| 前排/后排 | 至少 1 前排，后排有输出空间 | 无前排、全是脆皮 |
| 控制链 | 硬控 + 软控 + 反手 | 控制重叠或没有先手 |
| 开团/反手 | 既能开团也能反打 | 只会开团、不会撤退 |
| 清线/推塔 | 能守塔、能推塔、能打龙 | 没线权、被兵线锁死 |
| 机动性 | 追击、逃生、转线 | 笨重阵容被拉扯 |
| 视野 | 扫描、探草、保护眼位 | 被绕后、被蹲 |
| 打坦能力 | 百分比伤害、真实伤害、破甲 | 打不动前排 |
| 续航 | 治疗/护盾/回复 | 被消耗体系磨死 |
| 资源控制 | 打龙/打先锋速度 | 前期资源全放 |
| 强势期对齐 | 5 个英雄强势期尽量一致 | 有人前期、有人后期，节奏打架 |
| 经济曲线 | 是否依赖装备/雪球 | 劣势局无法翻盘 |
| 操作难度 | 阵容执行难度 | 高难度阵容容错低 |

## 9. 数据质量层

| 因素 | 说明 |
|---|---|
| 样本量 | 低样本的胜率不可靠（尤其 40+ 分钟、冷门英雄） |
| 置信区间 | 胜率差是否有统计显著性 |
| 版本漂移 | 跨版本数据不能直接混用 |
| 选择偏差 | 高 Ban 率英雄的胜率样本被压缩 |
| 生存者偏差 | 时长曲线受“谁先结束比赛”影响 |
| 段位/地区差异 | 韩服大师+ ≠ 国服翡翠+ ≠ 职业赛 |
| 分路归属 | 英雄多位置时数据要按分路拆 |
| 数据来源 | OP.GG/U.GG/Lolalytics/Riot API/赛事数据口径不同 |
| 模型校准 | 需要历史 BP/比赛结果做权重校准 |

## 11. 推荐的分层预测模型

```
BP Recommendation Score
= 版本优先级（胜率/BP率/补丁趋势）
+ 对位分（lane matchup）
+ 阵容结构分（伤害/前排/控制/清线/机动）
+ 体系匹配分（强开/Poke/分带/保护/抓单/突进）
+ 协同分（双人/中野/下路/上野/大招链）
+ 选手熟练度（英雄池/绝活/状态）
+ 对手针对分（Ban 价值/抢人价值）
- 风险分（样本不足/执行难度/被 Counter）
```

**建议实现顺序**：
1. **体系标签 + 阵容体系识别**（Poke / 分带 / 强开 / 保护 / 抓单 / 突进 / 团战）
2. **对位数据接入**（OP.GG Counter 页）
3. **阵容结构评分**（AD/AP、前排/后排、控制、清线、强势期）
4. **BP 顺序价值**（蓝红方、首抢、Counter 位、Ban 优先级）
5. **选手/对手因素**（手动配置，先做“英雄池/绝活”）
6. **历史数据校准**（赛事 BP + 结果）
